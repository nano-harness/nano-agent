# nano-agent Binary Execution Contract

[中文](./symphony-interop.zh-CN.md)

> This document codifies the stable interface contract for `nano-agent` binary
> execution (`nano binary exec`, `nano binary swebench`). Orchestrators such as
> `nano-symphony` rely on these invariants. Any breaking change to the items
> below **must** be coordinated with callers.

---

## 1. Exit Code Semantics

| Exit Code | Status        | Meaning                                              |
|-----------|---------------|------------------------------------------------------|
| `0`       | `success`     | Task completed normally                              |
| `1`       | (unclassified)| Unexpected / unhandled failure                       |
| `10`      | `needs_retry` | Transient failure (rate limit, timeout recoverable)  |
| `20`      | `abandoned`   | Permanent failure (classifier lockout, panic, etc.)  |
| `30`      | `timeout`     | Hard deadline exceeded                               |

Source: `pkg/cli/binary.go` constants `binaryExitSuccess`, `binaryExitRetry`,
`binaryExitAbandoned`, `binaryExitTimeout`, `binaryExitUnclassified`.

Orchestrators read the exit code to decide retry/abandon/success disposition.

---

## 2. stdout Protocol (Last-Line JSON)

`nano binary exec` and `nano binary swebench` **always** emit exactly one
compact JSON object to stdout — the **binary result summary**. This is the
**last line** of stdout output. Callers should parse the last non-empty line as
JSON.

### Schema: `binaryResultSummary`

```jsonc
{
  "status": "success" | "needs_retry" | "abandoned" | "timeout",
  "reason": "human-readable explanation (optional)",
  "termination_cause": "natural_completion" | "llm_failure" | "goal_max_turns" | "classifier_lockout" | "error_threshold" | "",
  "blocker_fingerprint": "stable identifier for dedup (optional)",
  "blocked_commands_sample": ["cmd1", "cmd2"],
  "tool_calls": 42,
  "duration_ms": 12345,
  "tokens": {
    "input": 10000,
    "output": 2000
  },
  "goal_state": { /* nullable, GoalState object */ },
  "cache_key": "sanitized_key (optional)"
}
```

**Critical invariant**: Even on panic, timeout, or error exits, the process
**must** emit a valid JSON line to stdout with at minimum:

```json
{"status":"abandoned","reason":"<error description>","duration_ms":0,"tool_calls":0,"tokens":{"input":0,"output":0}}
```

If stdout's last line is not valid JSON, orchestrators may fall back to a
`no_result_payload` classification and apply their own retry logic.

### Result file mirror

The same JSON is written byte-identically to `<output-dir>/result.json`.

## 3. File Artifacts

All artifacts are written under the `--output-dir` directory (typically
`<workspace>/.nano-out/` when invoked by an orchestrator).

| File                | Format              | Lifecycle                                   |
|---------------------|---------------------|---------------------------------------------|
| `result.json`       | Compact JSON        | Always written (byte-identical to stdout)   |
| `solution.patch`    | Unified diff        | Written only if working tree has changes    |
| `trajectory.json`   | JSON array          | Written on successful or partial completion |
| `sessions/`         | Internal session DB | Written when --output-dir is set            |

### `solution.patch`

- Generated by `pkg/patch.Generator.GenerateGitDiff()`.
- Diff is relative to `NANO_BASE_COMMIT` env (defaults to HEAD if unset).
- Orchestrators may read this file as the primary deliverable.
- If the file does **not** exist, the run produced no code changes.

### `trajectory.json`

- Pretty-printed JSON array of `trajectoryEvent` objects.
- Used for debugging and SWE-bench evaluation; not part of the primary contract.

## 4. Flag / Environment Variable Priority

### 4.1 Permission Mode

Resolution order (highest priority first):

| Priority | Source                              | Example                              |
|----------|-------------------------------------|--------------------------------------|
| 1        | `--dangerously-skip-permissions`    | Forces `yolo`                        |
| 2        | `--permission-mode=<mode>`          | `--permission-mode=acceptEdits`      |
| 3        | `NANO_PERMISSION_MODE` env var      | `NANO_PERMISSION_MODE=auto`          |
| 4        | Config file `permission_mode:`      | In `~/.config/nano/config.yaml`      |
| 5        | Default                             | `default`                            |

Valid modes: `default`, `acceptEdits`, `plan`, `auto`, `yolo`

Source: `pkg/cli/permission_resolver.go` → `ResolvePermission()`

### 4.2 Sandbox Configuration

Resolution order:

| Priority | Source                              | Effect                                        |
|----------|-------------------------------------|-----------------------------------------------|
| 1        | `--sandbox=off`                     | Disables sandbox regardless of env            |
| 2        | `--sandbox=on`                      | Enables sandbox with native backend           |
| 3        | `--sandbox=auto` (default)          | Enables only if orchestrator-spawned*         |
| 4        | `NANO_SANDBOX_ENABLED` env          | Overrides `sandbox.enabled` in config         |
| 5        | `NANO_SANDBOX_BACKEND` env          | Overrides `sandbox.backend` in config         |
| 6        | `NANO_SANDBOX_NETWORK_ACCESS` env   | Overrides `sandbox.network_access` in config  |
| 7        | Config file `sandbox:` section      | Base configuration                            |

*Orchestrator-spawned execution is detected when any of these env vars are set:
`SYMPHONY_WORKSPACE`, `SYMPHONY_MCP_URL`, `NANO_ORCHESTRATOR_PROFILE`.
These keys are part of the documented CLI contract and must not change.

**Important**: The `--sandbox` flag takes precedence over `NANO_SANDBOX_*` env
vars. When `--sandbox=off` is passed, the env vars are ignored. When
`--sandbox=on` is passed, the env vars may still influence `backend` and
`network_access` sub-settings (applied via `pkg/config` env override layer).

Source: `pkg/cli/binary.go` → `applyBinarySandboxMode()`; `pkg/config/config.go`
→ env overrides.

### 4.3 Session ID

Resolution order:

| Priority | Source                        | Example                         |
|----------|-------------------------------|---------------------------------|
| 1        | `--session-id=<id>`           | Explicit per-invocation ID      |
| 2        | `NANO_SESSION_ID` env         | Stable across retries           |
| 3        | `SYMPHONY_ISSUE_ID` env       | Orchestrator fallback           |
| 4        | Auto-generated                | `session_<hex>`                 |

Source: `pkg/cli/binary.go` → `resolveBinarySessionID()`

## 5. Orchestrator-Spawned vs Standalone Binary Mode

| Behavior                     | Standalone (SWE-bench)   | Orchestrator-spawned     |
|------------------------------|--------------------------|--------------------------|
| MCP auto-connect             | Disabled                 | Enabled                  |
| Sandbox auto-enable          | No                       | Yes                      |
| Hook service                 | From config              | From config              |
| OSS telemetry                | Disabled                 | Disabled                 |

Detection: `isEmbeddedBinaryExecution()` checks for `SYMPHONY_WORKSPACE`,
`SYMPHONY_MCP_URL`, or `NANO_ORCHESTRATOR_PROFILE` environment variables.

`nano-agent` does **not** embed any orchestrator-specific skill or MCP server
profile. An orchestrator that wants to auto-activate skills can set
`NANO_ORCHESTRATOR_PROFILE` to a comma-separated list of skill names; these are
added to `skills.auto_activate` at config load time. MCP servers must be
configured by the orchestrator (for example via `--mcp-config`) or by the user
config file.

## 6. Error Recovery Contract

When the process encounters an unrecoverable error:

1. `emitResult()` is **always** called before returning the error, ensuring
   stdout contains valid JSON even on failure paths.
2. The exit code is derived from the `status` field via `binaryExitCode()`.
3. Orchestrators should treat any non-zero exit with valid JSON as a structured
   failure (retry/abandon based on status).
4. Orchestrators should treat non-zero exit **without** valid JSON last line as
   `no_result_payload` — this indicates a crash before `emitResult` could run.

### Panic Recovery

A top-level panic recovery handler emits:

```json
{"status":"abandoned","reason":"panic: <message>","termination_cause":"panic","duration_ms":0,"tool_calls":0,"tokens":{"input":0,"output":0}}
```

This is handled in `pkg/cli/binary_cmd.go` via `emitPanicResult()`.

## 7. MCP Tool Naming Convention

When MCP tools are registered, the local tool name is `mcp_<server>_<tool>`,
for example `mcp_symphony_emit_result` for a server named `symphony` exposing
`emit_result`. Tool allow/deny patterns must use this single-underscore form:
`mcp_<server>_*` or `mcp_<server>_<tool>`.

---

## 8. Version Compatibility

This contract applies to nano-agent v0.7+. Changes to the contract fields
should be backward-compatible (additive only). Removing or renaming fields
requires a major version bump and coordinated orchestrator update.

| Field added               | Version | Notes                         |
|---------------------------|---------|-------------------------------|
| `cache_key`               | v0.7    | Optional, for retry dedup     |
| `goal_state`              | v0.7    | Nullable, goal evaluation     |
| `termination_cause`       | v0.7    | Structured enum               |
| `blocker_fingerprint`     | v0.7    | Stable dedup key              |
| `blocked_commands_sample` | v0.7    | Debug aide                    |
